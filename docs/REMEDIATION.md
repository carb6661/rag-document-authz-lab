# 修复建议与验证方式

## 核心修复

故意缺陷版只检查“有会话”和粗粒度角色，漏掉对象归属；修复版对每次读写执行租户→所有者/本租户管理员→动作权限判断。未知动作拒绝，资源不存在或范围不符都不返回文档。

修复不依赖前端隐藏、请求头中的租户或难猜ID。资源ID只是定位信息，不是授权凭据。列表也复用读取策略；仅修复详情接口是不够的。

## 将思路接入真实RAG

以下是下一步方案，**本仓库没有完成这些集成**：

1. 用生产IdP验证身份，依据可信组织关系获得租户；不要从检索正文或用户请求中生成身份。
2. 数据库在查询时加入租户及对象授权约束，使用事务/行版本处理写入；不要将全量文档先交给下游再过滤。
3. 切分块绑定可信的父文档ID、租户和权限版本，来源描述元数据不应直接决定访问权限。
4. 向量检索采用可信过滤条件，并在送入模型、返回引用前再次验证授权。
5. 在撤销共享、删除或调整权限后处理索引、缓存及会话的失效；增加跨租户、缓存污染和权限变化回归。
6. 处理失败时拒绝或返回明确缺口，不通过绕过授权保证问答“有答案”。

## 验证清单

- 重放 fixtures/cases.json，对比状态、对象内容和审计原因。
- 对所有角色/对象/动作逐项测试，合法操作保留、非法操作拒绝。
- 用另一个租户的同名用户访问，确认不能仅按用户名判断。
- 给请求增加 X-Tenant-ID 或受保护JSON字段，确认身份及归属不变。
- 验证版本冲突不覆盖新内容，拒绝请求不修改内存数据。
- 到期与撤销后再次请求，确认401；不要把一次成功当成永久授权。
- 通过真实回环HTTP复核，不仅依赖模拟客户端。
- 接入数据库/向量库后重新测试；当前通过不能迁移为下游安全保证。

生产还需要HTTPS、密钥/会话管理、限流、共享模型、集中审计、数据保留和多租户生命周期管理。本实验没有完成这些控制。
