# 0.3 技术修正：撤销竞态、旧快照与响应发布边界

验证日期：2026-10-17。修复前版本：0.2.0，提交 `9632b64cabf6790a651b71c8d4d48710a9252694`；修复后版本：0.3.0。

这是四份合成文档、五个演示身份上的本地实验，不是生产事故分析。上一轮输入、审计与检索改进见[历史报告](TECHNICAL_DEEP_DIVE.md)。

## 1. 存在的问题，以及为什么值得修

0.2版在请求开始时解析会话，再复制有权限的文档快照。慢评分发生在锁外，这有利于避免长时间占锁，但身份和文档之后都可能改变。

| 确定性插入的变化 | 0.2 实测 | 0.3 实测 | 根因与解决方案 |
| --- | --- | --- | --- |
| 评分期间撤销 Alice 会话 | 200，返回1项 | 401，无hits | 旧身份快照不等于仍有效；发布前重验原会话 |
| 评分期间正文更新、版本1→2 | 200，仍返回版本1 | 409，无hits | 旧候选不能代表当前状态；发布前比较版本 |
| 评分期间归属改为 Bob，故意不增版本 | 200，仍返回Alice原结果 | 409，无hits | 仅比较版本不足够；对当前文档重新执行对象授权 |
| 认证后、进入PATCH写入段前撤销 | 200，内存被修改 | 401，内存不变 | 认证与提交不是一个时间点；写入临界区重验会话 |

证据：[修复前](../examples/races-v020.json)、[修复后](../examples/races-v030.json)、[有限探针](../doclab/race_diagnostics.py)、[回归测试](../tests/test_checkpoints.py)。旧基线是在修改API前运行同一探针取得；探针本身不属于旧提交，不能声称旧版已有这些回归测试。

这说明本仓库存在时间变化下的陈旧授权/结果问题，不证明FastAPI框架有漏洞，也不表示发生了真实数据泄漏。不能用四个案例推导“消除了全部TOCTOU”。

## 2. 实际落地的设计

### 会话票据与锁内租约

`Sessions.authenticate()`返回不可变的内部`SessionTicket`，包含会话摘要标识与服务端身份。摘要不写入响应或审计，票据的repr也隐藏标识。原`resolve()`仍可返回身份，保留兼容性。

`Sessions.checkpoint(ticket)`持有会话锁，验证票据仍存在、没有到期、身份未变；返回仅当前线程、当前临界区可用的`SessionLease`。`lease.check()`可再次检查时间，因为即使撤销操作被锁挡住，时钟仍在走。临界区退出后或跨线程使用租约会报错。

所有涉及文档的检查遵守同一顺序：**会话锁 → 文档锁**。PATCH在这个短同步区域内完成授权、expected_version比较、更新模型校验，再次检查会话，最后赋值。撤销与写入检查由同一会话锁排序。

不是每次请求都持锁到结束。评分、JSON序列化、网络发送均在锁外；不能在临界区内调用另一个Sessions方法、执行await、网络I/O或不受信任的回调，否则可能死锁或拖住撤销。当前策略函数是受信、有限的本地纯计算。

### 响应发布前检查

端点在锁内记录候选证据：`(document_id, version, action)`。`PublicationGuard`在`/v1/`成功响应的ASGI `http.response.start`交给上层之前，通过线程池执行复核：

1. 原会话仍有效；不通过则401。
2. 证据中的文档仍存在、版本一致、当前对象授权仍允许；不通过则409。
3. 复核后再次检查会话期限。
4. 成功才转发原响应；失败用通用JSON替换，丢弃原正文、后续分片及trailers。

缺少会话票据的成功响应被改为401；缺少候选证据则500，避免以后新增受保护路由时静默漏检。没有命中时也要保存空证据并检查会话。原本的4xx拒绝不需要重验；健康检查和非HTTP作用域不在本层保护范围。

复核在线程池执行，避免同步等待锁阻塞异步事件循环。**锁在任何异步send之前释放**，不把慢客户端的接收速度变成阻塞撤销的条件。

最终替换发生在审计观察响应之前，因此审计的状态码、reason和实际应用响应保持一致；常规复核异常由外层生成通用500并记录，不回显异常原文。

### 为什么不直接重试

发生权限/版本变化时，返回409，而不是自动拿新权限继续回答。自动重跑可能扩大工作量、重复执行副作用，或者把调用者没看到的新版本偷偷当作旧版本处理。

对只读检索，客户端可以重新发起一次有界请求；对PATCH，先查明提交结果、重新读取版本，再由用户决定。**不能把401/409一律解释成“没有写入”，也不能盲目重试写操作。**

## 3. 已提交的修改，不等于还能安全返回

增加审计字段`mutation_committed`，只表示本次PATCH是否已完成内存赋值，不是数据库持久提交或事务日志。

| 变化时点 | 当前行为 | 审计含义 |
| --- | --- | --- |
| 写入检查之前已撤销/到期 | 401，不修改 | mutation_committed=false |
| 版本冲突/权限不符 | 409/404/403，不修改 | mutation_committed=false |
| 已写入，发布前才撤销 | 401，不返回原文，但修改保留 | mutation_committed=true，allowed=false |
| 已写入，发布前文档又变化 | 409，不返回旧结果；前次修改不自动回滚 | mutation_committed=true |
| 正常写入并通过发布复核 | 200 | mutation_committed=true，allowed=true |

`allowed`仅描述最终应用HTTP结果；它不是“是否发生副作用”的替代字段。内存审计没有对外查询接口，客户端无法靠读取审计自动判断自己的提交。实际服务应设计幂等键、受控操作状态查询与事务内事件；本项目没有伪造这些集成。

## 4. 仍然存在的窗口与取舍

- **最终检查不是网络原子操作。** 复核通过到实际发送之间仍有窗口；测试明确在最终检查刚结束后撤销，当前读仍可能200，下一次请求401。无法撤回已发给客户端或模型的内容。
- **不是对外部模型的中止机制。** 当前只有本地关键词评分。如果接入不受信任的远程重排/LLM，必须在交付内容前另设检查，响应前检查不能阻止此前已发生的外传。
- **候选证据偏保守。** 记录全部初始获准候选，不仅top_k命中。非命中候选变化也可能409，甚至最终本来是空结果；这样减少旧快照漏检，但提高重试率。当前四份样本可接受，生产要评估权限版本和一致性策略。
- **只保护已记录候选。** 不检测后来新增的可见文档，不保证完整可串行化查询。可信存储必须确保正文修改增加版本、ACL修改经过受控流程；偷偷同版本改正文不在版本检测承诺内。
- **仅单进程。** 会话、锁、数据、审计均在内存；多worker或多机各有状态，没有跨实例撤销传播。重启会清空。没有生产压测或最大撤销延迟承诺。
- **不替代请求与队列限流。** 锁段在本实验有限，但线程池等待、服务器排队、过载、连接中断及崩溃仍需单独设计。
- **认证策略没有升级成完整IAM。** 没有真实IdP、动态组织角色、共享权限或紧急授权。改变真实角色时应撤销旧会话并从可信源重新签发，不能信任客户端自报角色。

[ASGI规范](https://asgi.readthedocs.io/en/latest/specs/www.html#response-start-send-event)区分响应开始和响应正文事件；这里的“发布检查点”是应用内事件边界，不是客户端收到字节的证明。

## 5. 如何验证，而不是只看代码

```bash
python -X utf8 -m pytest -q
python -X utf8 -m doclab.race_diagnostics
python -X utf8 -m doclab experiment
python -X utf8 -m doclab.live_smoke
python -m pip check
```

实际本地结果：Windows / Python3.12.8，**200项测试通过**，比0.2新增36项；16组缺陷/修复对照共32请求满足预期。黄金报告升级schema_version=3，审计新增mutation_committed。历史探针文件保持原样。

新的回归覆盖评分中撤销/到期/版本/归属/租户/删除变化、所有受保护端点认证后撤销、锁内到期、已提交写入后撤销、最终检查后残余窗口、空结果复核、丢弃旧分片/trailers、复核故障审计、缺失证据拒绝、租约线程/生命周期和撤销锁排序。同步测试使用事件和显式插入点，不依赖sleep碰运气，不声称模拟了所有调度顺序。

真实回环HTTP额外验证：旧快照409、重新读取版本2成功、评分中撤销401且无原hits、后续读取401。测试服务器随脚本结束关闭；不使用外部目标、不打印会话值。

跨平台结果以对应提交的GitHub Actions为准，不能由本地通过推定。发布扫描仍有3项运行时会话变量赋值匹配，经逐项审查不含硬编码秘密；这不是零匹配或无泄漏证明。

## 6. 后续生产方案，尚未实施

最终方案不是“再加一把Python锁”。应先明确撤销的一致性等级，再落地可信身份平台、集中TTL会话/权限版本、带租户约束的持久查询和事务条件更新，协调索引/缓存失效，并设计幂等操作状态和持久审计。

每次跨越文档存储、重排器、模型和响应这些不同信任边界，都应独立定义授权检查点、失效策略及故障拒绝方式。必要时采用可取消任务与短期交付凭据，但已交付内容仍不能收回。

面试可以展示：复现旧结果 → 解释认证/提交/发布的不同时间点 → 实施双检查点与锁顺序 → 用状态和副作用双重验证 → 主动指出最终发送窗口与多进程限制。不要把这项合成实验说成企业上线经验或完整RAG安全认证。
