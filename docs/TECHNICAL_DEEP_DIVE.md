# 项目技术深挖：问题、根因、落地修复与生产方案

核验日期：2026-10-16。旧版基线提交：5408e89，版本0.1.0；本轮版本0.2.0。
本报告针对 RAG Document Authorization Lab，不是对其他仓库或真实企业系统的渗透测试。

## 一、结论先行

旧版的对象级权限矩阵在本轮原有回归中保持正确，但“对象权限检查存在”不等于整个服务可靠。输入解析、资源边界、故障审计、会话生命周期和检索路径都需要独立验证。

本轮修复了五个可复现的工程问题，增加先授权再评分的精确关键词检索，以及主体级会话撤销。仍然是单进程合成实验，未变成可直接公网部署的生产RAG。

证据：[旧版观察](../examples/baseline-v010.json)、[新版观察](../examples/hardening-v020.json)、[16组对照](../examples/report.json)、[专项回归](../tests/test_deepening.py)。

## 二、复现与修复结果

| 问题 | 0.1.0实测 | 0.2.0实测 | 原因与实际修复 |
| --- | --- | --- | --- |
| 重复JSON成员静默覆盖 | text出现两次仍200，保存last | 422，文档不变 | 普通JSON解码只保留最后值；网关使用object_pairs_hook拒绝重复成员，再做Pydantic字段校验 |
| 重复Authorization不明确 | 两个有效身份头被接受，200 | 400，尚未进入认证 | 不同读取路径可能选不同头；在读取正文前拒绝重复认证、Host、Content-Type、Content-Length |
| 常规未处理异常漏审计 | 故障注入500，审计0条，无关联ID/no-store | 500，审计1条，关联ID及no-store存在 | 旧中间件只在正常返回后记日志；捕获常规异常，生成通用错误并记录结构化内部原因 |
| 字节上限不限制空消息帧 | 1501个空ASGI帧全部存储/转发 | 接收第1025帧时413，不转发 | 空帧不增加字节计数；改为单一字节缓冲、帧数上限及总正文读取期限 |
| 过期会话积累 | 三个过期会话后再次签发，容器共4项 | 再签发后仅1项 | 旧版只在解析该令牌时删除；签发前清理、显式清理、容量限制且不静默挤掉活跃用户 |

注意证据的边界：

- 重复输入表明解析歧义，并未证明绕过原有对象权限或在反向代理上成功利用。
- 异常审计问题由测试注入一个RuntimeError复现，不表示生产已经发生事故。
- 空帧是直接驱动ASGI的有限模拟；未用真实网络实施DoS，不保证外部请求会被服务器拆成相同帧。
- 没有公开令牌签发路由，过期会话问题属于受信签发方的容量维护，不应包装成匿名远程攻击。
- 这些是本仓库观察，不是FastAPI、Starlette或JSON标准的通用漏洞公告。

## 三、为何只有Pydantic还不够

Pydantic负责字段类型、长度、枚举及额外字段限制。它看到的已经是JSON解码后的对象，无法还原被覆盖的重复成员。

因此采用分层处理：

1. 有界读取原始请求，拒绝关键头歧义。
2. 严格UTF-8 JSON对象解析，拒绝重复成员、NaN/Infinity、非有限数及非法结构。
3. 再由Pydantic检查字段、长度及业务输入。
4. 再从服务端会话解析可信身份。
5. 最后进行对象/动作授权与版本检查。

[RFC 8259 第4节](https://www.rfc-editor.org/rfc/rfc8259#section-4)建议对象成员名称唯一，并说明不唯一时实现行为不同；本项目选择严格拒绝以减少歧义，不把它描述为标准对所有解析器的强制要求。

当前仍在认证之前有限读取正文，不能替代网关的连接数、速率与并发配额控制。实际传输层的长度/分块规则由服务器和代理处理，本模块不是完整的HTTP请求走私防护。

## 四、资源保护的取舍

默认正文最大64KiB、最多1024个ASGI请求消息帧、读取总期限5秒。期限覆盖整个正文读取，而不是每个片段重新获得5秒；读取后仅回放一个完整消息。

这三个维度不同：字节限制内存规模，帧限制空消息或碎片处理，期限限制持续等待。阈值是本地原型默认值，不是经过生产流量调优的结论。

合法的慢客户端或极碎片化请求可能被拒绝；接入真实网关时应依据可信流量配置和测试。这个期限不是整条请求、模型推理或数据库操作超时。取消任务可能只有内部499审计标记，并不承诺网络上仍能返回错误响应。

## 五、故障审计为何需要单独设计

新增审计字段包括UTC时间、递增序号及覆盖计数；256条缓冲被覆盖时，audit_meta.dropped增加，不再无声丢掉“已经丢了多少条”的线索。通用500包含服务端关联ID，正文及审计不保存异常原文、令牌或文档内容。

这与[OWASP日志建议](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)的最小化敏感数据、关联及错误事件记录方向一致，但这里只实现了内存实验。

还没有解决：

- 进程崩溃、被终止或机器断电时不能保证日志持久化。
- 时间戳与序号不是签名或不可篡改保管链。
- 缓冲计数不能恢复被覆盖的事件。
- 请求响应成功后，最终网络传输是否完整不由这条审计证明。
- 没有受控的服务端堆栈日志；生产排障需单独设计受权限保护的错误追踪，不把原始异常直接发给用户。

## 六、让项目真正进入检索路径

新增 POST /v1/retrieve：精确关键词检索，不是语义向量检索或大模型问答。

流程：

服务端会话身份 → 同一策略过滤候选文档 → 锁内复制授权快照 → 对快照评分 → 限制top_k → 返回片段及文档版本引用。

验证不仅检查“最终响应没有他人数据”，还给评分函数加观察点，确认被拒绝文档从未进入评分。这样避免把全量文档先送入重排器/外部模型，再在最后过滤。

接口只允许query和top_k，不能由调用者指定tenant_id、owner_id或role；匿名请求401。版本引用来自服务端文档快照，不是用户提供的标准名或Markdown元数据。

边界：

- 当前内存程序仍持有全部四份样本，授权前会查看资源元数据；这是“授权后评分”，不是证明数据库或向量库已经执行安全下推。
- 字面匹配按空白分词、大小写折叠，最多8项查询词；中文整句可能不命中，没有分词模型、同义词或语义理解。
- score是词频计数，不是可信度、合规分数或概率。
- snippet仅为正文前240字符，不保证覆盖所有匹配处；matched_terms说明匹配词，引用只定位合成文档ID及版本。
- 并未自动接入Compliance RAG Assistant，也没有标准原文行号引用或LLM答案授权。

## 七、撤销竞态：这一版仍然保留的已知限制

revoke_subject(tenant_id,user_id)会在本进程撤销该成员所有当前会话，不影响其他租户同名用户。新请求将401。

但身份在请求开始时解析为不可变快照。专项测试在评分期间执行撤销，当前请求仍可返回已经授权的快照，新请求则401。这是明确记录的检查点语义，不是“实时终止一切访问”。

生产应先定义授权语义：

- 请求开始时快照有效，是否允许请求完成？
- 权限变化后，是否必须在送入模型前或返回引用前再次检查？
- 长任务如何接收权限版本变化及中止信号？

多次复核能缩小窗口，但无法撤回已经发送给模型或客户端的数据，也无法消除最终检查到网络发送之间的所有竞态。不能承诺“撤销后已发送数据自动消失”。

## 八、生产最终架构建议（未部署）

| 层 | 建议方案 | 必须补的验证 |
| --- | --- | --- |
| 身份 | 审核过的OIDC/IdP，可信租户成员关系，短期凭据及权限版本 | 发行者/受众、撤销、角色变化、同名跨租户 |
| 文档存储 | PostgreSQL等持久库，租户作用域查询、适当RLS、版本条件更新 | 连接池上下文复用、跨租户SQL、并发冲突及回滚 |
| 会话/撤销 | 集中TTL会话或版本缓存，多进程一致策略 | 失效传播、缓存陈旧、后端故障时的拒绝策略 |
| RAG入库 | 可信父文档ID绑定chunk，ACL与正文/描述元数据分离 | 不能用Markdown里的tenant_id决定访问权 |
| 检索 | 数据源过滤，重排/送模型前授权，必要时返回前再次检查 | 过滤条件被忽略、缓存污染、权限改变、引用泄漏 |
| 审计 | 受控持久事件存储、统一时钟、最小化字段和保留策略 | 队列失败、写入失败、重试重复、覆盖及访问审计 |
| 网关 | TLS、认证前限流、并发配额、请求/任务期限和隔离部署 | 慢客户端、容量、租户公平性、网关/应用策略一致 |

数据库可使用类似“文档ID+租户+授权范围+expected_version”的条件更新，并检查受影响行数；不能仅把当前Python锁搬到多进程部署。RLS与应用授权是分层控制，不是互相替代。

对高价值审计，应明确写入失败时是阻止业务还是受控降级；可采用事务内事件/Outbox等设计，但该仓库尚未实现数据库或消息队列。选具体云服务及身份平台会涉及成本和配置，需要另行决定。

## 九、实际验证与如何讲项目

本地164项测试通过；原有角色/对象/动作矩阵保留，新增输入歧义、帧/时间边界、故障审计、会话清理/容量/主体撤销、检索权限矩阵、评分函数观察及撤销竞态用例。16组固定对照共32次请求。真实回环HTTP还验证授权检索1项、仅出现在他人文档的关键词返回0项。

运行：

```bash
python -X utf8 -m pytest -q
python -X utf8 -m doclab.diagnostics
python -X utf8 -m doclab experiment
python -X utf8 -m doclab.live_smoke
```

面试可以按以下顺序讲：原始目标 → 有证据的问题 → 不能据此夸大的风险 → 分层修复 → 新回归证明 → 仍未覆盖的竞态和生产边界。

不要说“164个测试证明没有漏洞”，也不要把SQLite/Redis/PostgreSQL或OIDC架构建议写成已部署经验。
